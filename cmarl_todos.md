# ToDos for the Contextual MARL Experiments

1. I want to make sure that the OOD evaluation is actually out of distribution. For that I want to sample the training envs from a restricted env parameter value space, the ID evaluation envs from the same space and the OOD evaluation envs from below and above this value space, making sure OOD actually means unseen conditions. I guess for plotting it might be useful to sample only 1 parameter out of distribution per evaluation sample to really see the impact single env variations and how context affects coping with them but I am unsure so far. Maybe then also only 1 or 2 env parameters should differ from the default config during training? I don't know.
2. I want to evaluate more env configurations to be able to plot them in a way like Appendix C.2 of the paper "Dreaming of Many Worlds: Learning Contextual
World Models Aids Zero-Shot Generalization": plot the performance (return/iqm, y-axis) of single context variations (x-axis) with a highlighted "in-distribution-window". I would expect a trapezoid shaped curve with good ID performance and decreasing OOD performance. Eventually in the future I also want to create 2d plots of 2 modified env parameters to investigate non trivial parameter interactions.
3. Maybe I should seperate detailed evaluation from the training script. For the training script a few meaningful Key Performance Indicators (e.g. losses, return, successes) and Resource Management Metrics (e.g. ETA, memory) should be sufficient to quickly verify that the training was successful and the policy learned something. Currently the Tensorboard view is a bit overwhelming and contains confusing entries. E.g. some Rliable metrics like the IQM are supposed to be calculated for multiple runs and I don't really see the use of logging them in a single training run, rather log the values needed to calculate them for a whole experiment (but maybe don't add them to tensorboard). In general I think it is useful to log many metrics to have them available for advanced evaluation but don't show them in tensorboard. Also for a training performance heuristic you don't need as many evaluation runs as for an advanced evaluation using my desired metrics (rliable, transferability, sample efficiency). So my suggestion would be to run reasonably few evaluation runs in the training script (but still save the relevant for metrics these runs so that they can also be used for the advanced evaluation), reduce the training tensorboard load to a manageable amount of informative metrics and add an extra evaluation script which will run additional evaluation episodes, aggregate the metrics and prepare them to be plotted in the notebook.
4. Adapt the resource request in the slurm scripts to optimize for efficiency and not risk getting negative karma and longer waiting times. Of course I have to measure the real requirements again after implementing all the planned changes but my current efficiency leaves some room for improvement (CPU: 21% (orange), Mem: 68% (light green), Max GPU: 62% (yellow), Time: 48% (light orange)).

I haven't decided yet if I want to use default env 5 times (will the results vary significantly?) or only as one of the seeds. Whatever is more appropriate.
